# 直播运营分析：数据可得性与方案评审

更新日期：2026-09-17。

状态：研究与设计输入，尚未确定实施方案，不是已上线能力、API 契约或数据库规格。
当前暂停接入与开发：用户发现现有账户为企业账户，计划先改为个人账户；等待用户完成账户处理后再继续。
后续在本文持续完善研究结论；确定实现范围后再同步权威需求、架构、数据库、测试和开发计划，避免另建多套规格。

## 1. 已确认目标与边界

- 用户希望增加直播运营分析，关注人流量、弹幕热点和礼物，并按数据获取由易到难推进。
- **范围仅限直播期间的数据及其复盘，不做录播投稿视频的播放、互动或传播效果分析。**
- 用户已申请直播创作者服务中心，并确认持有 `BILIBILI_ACCESS_KEY_ID` 与 `BILIBILI_ACCESS_KEY_SECRET`；
  无需重新引导入驻。尚未确认 AppId、项目状态或目标主播身份码，也未用凭证调用接口。
- 用户说明凭证存于开发电脑 `~/.bashrc`；本轮未读取其值，不将凭证内容写入仓库。
  用户正在处理企业账户改为个人账户；迁移方式、能否保留项目、原凭证和权限是否继续有效均未核实。
- **可以使用普通观众账号**，无需再次确认这一前提；当前没有提供凭证或完成账号接入。
- 当前方案不依赖目标主播的账号、Cookie、后台权限或授权。主播主动 OAuth 授权/提供身份码是未来可选路径，不能默认为已获授权。
- 普通观众登录态、开放平台 OAuth access token、直播互动玩法身份码是不同凭证，不能互相代替。
- Analytics 应保持可选、可失败、可重算，不影响 Recording、存储、Bilibili/COS 发布与 Songs。
- 本轮只记录调研，不修改生产代码、Recorder 配置、数据库、外部依赖或部署。

## 3. 常用分析方法

成熟直播分析常区分并发观看、累计观看、观看时长和聊天速率；这些定义可供参考，不能把其他平台后台能力当作 B 站观众端能力。[S1]

| 方法 | 运营问题 | 本项目应用方式 |
| --- | --- | --- |
| 单场复盘与分钟趋势 | 哪段热闹、何时发生变化？ | 先做弹幕曲线、有效去重人数、热点片段 |
| 同类场次对比 | 内容或开播时段是否改善效果？ | 同时比较总量、每小时指标；控制时长、时段、抽奖/PK 等因素 |
| 漏斗 | 观看→互动→关注→付费哪里流失？ | 只分析有可靠分母的可观测子集，不拼接成完整观看漏斗 |
| 用户分群/回访 | 互动者是否回来、支持者是否扩大？ | 需要稳定标识、明确历史观察起点与连续采集 |
| 贡献集中度 | 是否依赖极少数支持者？ | Top 1/Top 10 贡献占比、贡献人数、按场/周对比 |
| 内容热点 | 什么话题引发讨论？ | 词组、突增、代表原文、人工内容标签；AI 后置 |
| 内容效果分析 | 某节目是否促进互动/送礼？ | 先做时间关联，不能直接当因果或精确 ROI |

## 4. 观众视角的数据可得性

普通登录观众是当前允许的采集身份。blivedm 的示例说明游客模式可能隐藏用户名并把 UID 置为 0；
因此登录有助于用户去重，但仍须实测，不能保证全量或始终返回稳定标识。[S2]

| 数据/指标 | 获取难度 | 可承诺口径与限制 |
| --- | --- | --- |
| 开播、标题、分区、可观测时长 | 低 | 区分直播开始、录制开始、采集开始 |
| 弹幕文本与时间 | 低 | 已采集弹幕；消息数量不是人数 |
| 去重发言/互动人数 | 低至中 | 仅对有效标识去重，单列未知身份消息比例 |
| 热词、高能片段 | 低至中 | 表达发言群体反馈，不代表沉默观众 |
| 礼物、SC、上舰数量 | 中 | 依赖采集开关、协议版本和缺失情况 |
| 已观测礼物价值 | 中 | 需金额、币种、数量语义；不等于实付总额或主播到账 |
| 平台展示看过数、热度、高能用户数、点赞计数 | 中 | 分开存储、命名与解释，不统一叫在线人数 |
| 进场、关注、分享事件 | 中至高 | 已观测事件，不承诺完整覆盖 |
| 粉丝数快照变化 | 中 | 接口待验证；净变化不等于本场新增关注 |
| 跨场互动回访 | 中至高 | 需要连续历史和稳定标识；不是观看留存 |
| 精确同时在线、真实 UV、平均观看时长 | 当前无可靠方案 | 未找到普通观众授权即可取得目标主播完整指标的官方能力 |
| 曝光/流量来源、完整观众画像、结算收入 | 当前范围外 | 不通过公开事件猜测后台数据 |

社区事件模型分别定义了 `WATCHED_CHANGE`、热度心跳、`ONLINE_RANK_COUNT`、点赞和进场/关注事件。
它们可作为采集候选，不能把库变量名中的 online 当成人数定义。[S3]

产品建议：把“人流量”拆成平台展示趋势、已观测进场、去重发言和窗口互动人数。
看过数增长不直接解释为新增唯一观众；指标发生重置或口径变化时保留断点，不填造连续曲线。

## 5. BililiveRecorder 2.18.0 的具体限制

### 5.1 配置

| 配置 | 固定版本默认值 | 作用 |
| --- | --- | --- |
| `RecordDanmaku` | false | 总开关 |
| `RecordDanmakuRaw` | false | 在已保存消息上增加原始数据 |
| `RecordDanmakuGift` | false | 普通礼物 |
| `RecordDanmakuSuperChat` | true | SC，仍受总开关限制 |
| `RecordDanmakuGuard` | true | 上舰，仍受总开关限制 |

以上由固定版本配置与官方设置文档核对。[S4]
我们目前的 `DesiredProfile` 和 HTTP 配置同步管理总开关，没有显式管理这些子开关。
生产可能有既存全局/房间设置，因此不能仅凭本地实现判断生产未录礼物。

### 5.2 保存内容

固定版本 writer 只保存普通弹幕、SC、礼物、上舰。普通弹幕有文本、时间、用户名及 UID；SC 保存价格；
礼物默认保存名称与数量，上舰默认保存等级与数量，后二者不单独保存金额。`raw` 保存对应消息数据，
**不是所有 WebSocket 消息的完整归档**，不能补出看过数、进场或热度。[S5]

历史文件缺少 raw/金额时，不按当前目录价格硬补“历史精确收入”。官方提示开启 raw 会增加文件体积，
应在样本中测量实际增量及保留成本。[S7]

### 5.3 协议兼容

固定版本 parser 识别 `SEND_GIFT`，未实现 `SEND_GIFT_V2`。[S6]
biliLive-tools 的变更记录和 LAPLACE ws 已出现 V2 支持/说明，后者提示一条盲盒消息可能含多个礼物。[S8][S9]
这是需要验证的漏采风险，不是目标房间已经漏采的定量结论。开启 raw 无法挽救在 writer 之前被忽略的事件。
不得为分析功能自动升级 Recorder；版本变更必须独立评审和测试。

## 6. 采集路线比较

| 路线 | 收益 | 局限/成本 | 评审建议 |
| --- | --- | --- | --- |
| 已关闭 XML 离线分析 | 最易接现有索引；历史可重算 | 受已有字段限制，非实时 | 优先 |
| 补齐 Recorder 子开关/raw | 保存未来分析所需字段 | 协议覆盖、体积、配置同步要验证 | 优先试验，尚未实施 |
| 观众端 HTTP 低频快照 | 房间展示数据与变化趋势 | 接口、频率、鉴权与字段待实测 | 后续补充 |
| 独立观众端长连接 | 更多事件与实时统计 | 鉴权、心跳、重连、缺口、去重、协议维护 | 明确需要后再引入 |
| Recorder 用户脚本转发 | 复用连接的可能性 | 固定版本回调受四类 writer 事件过滤；同步网络路径 | 不作为主要方案 |
| 浏览器/OCR | 对照可见数据 | 高资源、布局变化、展示值舍入 | 仅用于核验 |
| 第三方统计服务 | 可能补历史或对标 | 覆盖、授权、口径、导出、价格需逐项确认 | 交叉验证，不作唯一事实源 |
| 官方 Open API | 文档化事件与授权数据 | 不等于任意目标房间查询，见下一节 | 保留可选接入 |

Recorder 用户脚本提供同步 `fetchSync`；不建议把逐消息远程请求放进录制侧路径。[S10]
biliLive-tools 的弹幕密度、关键词跳转和高能片段交互可供参考，不因此替换现有录制/发布体系。[S11]

## 7. 官方 Open API：实际能帮助什么

### 7.1 必须区分三种接入

| 接入 | 身份/授权 | 对当前约束的适用性 |
| --- | --- | --- |
| 观众网页登录 Cookie + Web HTTP/WS | 普通观众登录态 | 当前允许，但这是客户端接口路线，不是官方开放平台授权 |
| 直播创作者服务中心/互动玩法 | 开发者凭证、AppId、目标主播身份码 | 需要主播配合；不需要把主播密码交给我们。[S12] |
| 通用开放平台 OAuth 直播能力 | 应用获批权限、用户授权、直播能力单独报备 | 不能把观众授权等同于目标主播授权。[S13][S14] |

官方 OAuth 文档描述的是授权用户资源；可调用权限还取决于应用已获批的 scope。
普通观众账号授权自己的数据，并不赋予我们其他主播的直播后台权限。[S14]

OAuth 直播接入指南明确要求单独申请报备，且与互动玩法使用不同接口和鉴权。
申请材料包括应用及业务场景；当前项目是否能通过审核需要平台确认，不能假设注册即可使用。[S13]

### 7.2 直播长连接能力与局限

已查到 OAuth 直播的 `POST /arcopen/fn/live/room/ws-start`，使用 Access-Token 和应用签名；
公开示例没有任意目标 room_id 参数，并包含授权用户未开通直播间的错误示例。
结合授权机制，应按授权用户房间评估；没有找到凭普通观众授权即可任意订阅其他主播的官方入口。[S15]

CMD 文档列出弹幕、礼物、SC/下线、大航海、点赞、进场、关注和直播状态事件。消息标识有利于去重；
用户使用 open_id，union_id 默认可能为空且需要另申请。进场推送会受负载限流，未提供可靠退出事件。
因此官方长连也不能直接还原精确在线人数/观看时长；这些身份字段不得与 Web UID 直接合并。
文档个别 CMD 正文与 JSON 示例前缀不一致，接入前仍需真实脱敏 fixture。[S16]

### 7.3 房间基础/详细信息

官方房间基础信息示例有标题和直播状态；详细信息有主播、分区、封面、开始时间等，
所查响应没有完整观看时长或结算数据。不能把“详细信息”接口解读为完整运营后台。[S17][S18]

### 7.4 本次不纳入的官方能力

官方能力目录也包含视频稿件与相关统计，但用户已明确排除录播投稿视频分析。
不为本任务申请稿件分析权限、接入投稿账号 OAuth 或扩展发布核验；官方能力评估聚焦直播数据。[S22]

### 7.5 研究结论

- 待用户完成账户类型调整后，再确认开发者凭证是否有效、项目 AppId/状态，以及目标主播身份码是否可获得，最后核实实际事件。
  Access Key 用于开发者鉴权，不等于目标房间授权；官方示例还要求 AppId 与主播身份码。[S12]
- 普通观众账号 + 已有 XML 保留为可选方案，不因官方申请就假定其能力已可用或已被替代。
- 如未来主播愿意配合，可进一步评估身份码或 OAuth 直播事件，具体可用集合分别验证。
- 录播投稿视频分析已明确排除，不列入后续实施范围。
- 没有找到普通观众授权即可获取任意主播完整实时在线、观看时长、流量来源或结算收入的官方接口；
  这是本次公开资料核查的边界，不宣称平台不存在任何特殊合作能力。

### 7.7 OpenLive 数据与可交付功能清单

本节专指用户已申请的 **直播与互玩 OpenLive**，不将 7.2 的 OAuth 能力自动并入。
依据已归档的 [长链命令说明](references/bilibili-open-live/2026-09-17/pages/f9ce25be-312e-1f4a-85fd-fef21f1637f8.md)、
[应用 API](references/bilibili-open-live/2026-09-17/pages/eba8e2e1-847d-e908-2e5c-7a1ec7d9266f.md) 和
[常见问题](references/bilibili-open-live/2026-09-17/pages/5dffc297-6fd2-41ff-bd45-6e8b89e2a68e.md)。
以下是文档声明的能力，尚未验证本项目权限、真实字段或接收完整性。

| 数据 | 候选功能 | 必须保留的限制 |
| --- | --- | --- |
| 弹幕文本、时间、消息 ID、用户 open_id、表情类型 | 分钟弹幕量、去重发言人数、关键词、话题变化、刷屏与峰值 | 发言者不能代表全部观众；消息去重与内容降权分开 |
| 礼物名称、数量、价格字段、付费标记、赠送人、连击和盲盒信息 | 礼物排行、送礼人数、价值曲线、贡献集中度 | 价格、连击累计/增量和盲盒需样本确认；展示价值不等于主播到账 |
| SC 文本、金额、用户、时间及下线事件 | SC 汇总、留言热点、互动时间线 | 下线不自动等于退款 |
| 上舰用户、等级、数量、单位、价格 | 本场上舰记录、等级分布、价值趋势 | 不能直接得到有效舰长总数，也不能仅凭单条事件判断首开或续费 |
| 点赞用户、时间、聚合次数 | 点赞趋势、参与人数、互动高峰 | 单用户最近两秒聚合；应累计 like_count，不能把消息条数当点赞次数 |
| 进场用户 open_id、时间 | 已观测进场趋势、去重进场人数、重复进场 | 高峰动态限流；没有明确离场事件，不承诺完整访客数 |
| 开播/下播事件，开播时标题与分区 | 场次划分、时长、按场次对比 | 中途接入和断线可能漏事件，采集会话不等于完整直播场次 |
| 互动用户 open_id、部分事件的粉丝牌和大航海等级 | 活跃用户、粉丝牌分层、跨场互动回访 | open_id 作用域为开发者与应用；UID 已废弃，union_id 需另申请；不能推断完整观众画像 |

仅凭这些事件不能可靠提供：真实实时在线、完整观看 UV/PV、平均停留时长、观看留存、
曝光和流量来源、完整关注转化、主播结算收入。进场与互动统计均使用“已观测”口径。
文档化实时推送不等于历史查询或断线补发；历史追溯与补采能力需另行确认，不能承诺补齐未采集场次。

### 7.8 后续候选交付与恢复条件

用户本轮只要求整理并留档，**不启动 API 联调、采集器开发或配置变更**。
账户调整由用户先处理；不假定个人账户已切换成功，也不假定企业账户凭证能沿用。

待恢复后，功能候选按以下顺序评审；这是产品建议，不是已排期或已批准的实施方案：

1. **单场基础报表**：弹幕与发言人数、礼物与送礼人数、SC、上舰、点赞、分钟曲线和采集缺口。
2. **弹幕热点**：关键词、突增时段、代表性原文；话题聚类与 AI 摘要在基础统计验证后考虑。
3. **礼物专题分析**：分类、已观测价值、连击/盲盒处理、贡献集中度；金额样本不足时先提供数量。
4. **录像高光定位**：将互动峰值映射到原始录像时间点，生成可人工确认的候选片段；
   这是直播内容复盘，不是录播投稿视频的数据分析，不自动剪辑或投稿。
5. **跨场及内容效果**：首次观测互动者、回访、节目/歌曲时间段对比；只描述关联，不能证明内容导致收入增长。

恢复前后需依次确认：

- 用户完成账户处理并希望继续；核实接入平台仍为 OpenLive、当前开发者资格及凭证状态。
- 核实项目 AppId、项目类型/状态、消息权限和目标主播身份码授权；普通观众账号不能代替主播授权。
- 选定获授权的测试房间，保存脱敏事件样本，验证签名、心跳、去重、断线和各项统计口径。
- 比较官方事件与现有 XML 路线，确定首版数据源、是否需要直播中实时展示、缺口和保留策略。
- 按仓库流程更新需求、架构、数据库（如涉及）、API、测试与开发计划后再实现。
  当前实时二次采集非目标不因本研究自动撤销。

## 8. 建议指标与分析口径

### 弹幕与热点

- 一分钟弹幕量与有效标识去重人数并列；滑动五分钟互动人数不能当同时在线。
- 词组频率、相对附近时间窗的突增、代表性原文与时间定位；先用统计和人工标签，再加 AI 摘要。
- 原始量与去重复/降权结果分开，保留刷屏率；多人同文不应一律删成一条。
- 抽奖、PK、唱歌、聊天独立标注，避免把抽奖口令或单人刷屏解释成广泛内容认可。
- AI 摘要附可核查证据；情绪分类先以人工样本检查反讽、梗和上下文误差。

### 礼物

- 礼物、SC、上舰分别统计，免费与付费分别展示；金额缺失为 unknown，不当作 0。
- 保存币种/单位、数量语义和来源版本，明确单价、累计连击量及增量，避免重复乘算。
- 盲盒投入、产出展示价值和主播结算分开，不能同时加总为一笔收入。
- 指标优先顺序：事件/数量 → 可识别贡献人数 → 已知价值 → 集中度/跨场支持变化。
- 同一场同时有 XML 和 WS 时，先定义主来源和去重规则，不能把两份采集合并相加。
- SC 下线事件不自动等于退款；不能从消息撤回自行反推结算变动。

### 回访与比较

- “首次观测互动者”只表示在当前数据历史里首次出现，不叫新观众或新粉丝。
- “后续三场互动回访率”分母为本场有效互动用户，分子为其中在接下来三场再次互动者；
  需等三个后续场次完整到齐，不把观察不足的人群算流失。
- 每场指标同时报告样本/缺口、时长、内容类型与时段；不同采集方式/协议版本不直接混合比较。
- 观看人数不可用时不计算全体观众付费转化率；任何子集转化必须明确共同分母。

## 9. 数据与架构设计输入（待确认）

- 先复用闭合 XML 与现有原始资产索引；分析结果独立版本化、幂等重算，不依赖视频已上传或审核通过。
- 原始数据留文件，SQLite 保存统计和必要索引；不默认把全部弹幕正文灌入业务库。
  如需全文检索/明细持久化，先明确体积、保留、权限，再更新 DATABASE.md。
- 统计基于原直播时间与真实断流间隙，不基于压缩掉间隙或删减后的发布时长。
  视频剪辑/重分组不应改写历史观众反馈；回放跳转另做时间轴映射。
- 文件存在且有弹幕不代表整段采集完整；“首末消息间隔”不是连接覆盖率。
  区分无互动、未采集、连接中断、身份未知、未解析协议；未知区间不填零。
- 身份键应包含来源与适用范围，不能把 OAuth open_id、union_id、Web UID 或打码昵称直接拼为同一个人。
- 观众凭证按现有加密和不回显机制设计；与上传账号用途分开，不将凭证写入文档、fixture 或日志。
- 新采集循环有独立错误、重连和资源上限；不使用一个永不结束的任务占住现有业务 worker slot。
- 当前 REQUIREMENTS.md 将实时弹幕二次采集/WebSocket 基础设施列为非目标。
  本研究不撤销这一约束；如果选择长连接方案，再在设计阶段显式调整。

## 10. 从易到难的建议步骤

| 步骤 | 交付 | 进入下一步前的证据 |
| --- | --- | --- |
| 0 数据审计 | 真实 XML 类型、UID、raw、金额、时间范围报告 | 固定版本脱敏 fixture，生产子开关核对，目标房间新事件探测 |
| 1 单场互动复盘 | 指标卡、分钟曲线、热词、热点原文、CSV | 多段/重复导入不重复计数，未知身份和缺口不造数 |
| 2 礼物分析 | 分类、已观测价值、贡献集中度 | 礼物协议、币种、连击、盲盒及去重口径经过样本验证 |
| 3 流量趋势 | 展示计数快照；必要时增加独立事件采集 | 字段定义、权限、限流与重连可用性；更新原非目标 |
| 4 跨场与内容效果 | 互动回访、内容标签对比、可追溯 AI 复盘 | 足够连续历史，稳定身份与人工验收样本 |

首个建议闭环：**单场互动复盘页**，由 XML 分析支持；暂不以精确流量或总收入为验收承诺。
以上为候选顺序；当前等待用户处理账户类型，恢复后先核实现有官方项目和目标房间授权条件，
再确认首版数据来源及是否需要直播中实时展示。官方接入路线的功能候选与恢复条件见 7.8。

## 11. 待验证清单与测试设计输入

- 普通观众登录与游客的对照：有效 UID 比例、事件种类、连接稳定性；不要求用户再次确认观众账号方案。
- 实际 Recorder 配置与 XML 中礼物/SC/上舰/raw 是否一致；配置变更应等待后续具体实施任务。
- `SEND_GIFT_V2` 等新协议是否在目标房间出现，固定版本漏采范围如何；不能仅因没有记录就判定没有送礼。
- 断流续播、分段、重复导入、跨文件重复、同一秒合法重复消息、缺失/损坏 XML、来源文件清理后的重算行为。
- 身份为 0、匿名/神秘用户、昵称变化；有标识子集统计与未知数量分别展示。
- 价格缺失、免费礼物、连击增量/累计、盲盒、SC 下线、上舰单位；金额使用确定的单位和精度。
- 来源版本、算法版本、分组版本记录；采集失败不能改变 Recording 或其他模块状态。
- 本轮官方 API 只做文档核查：用户已有直播创作者服务中心开发者密钥，但正在处理企业账户改为个人账户；
  账户调整后的凭证有效性、项目状态、AppId、目标主播身份码均未确认，联调与开发暂缓。
- 针对现有项目核对：接入平台、获批能力、可访问的房间范围、事件清单、历史数据能力、频率/限流及字段说明；
  讨论使用权限页面和脱敏响应，不在文档或对话中记录密钥、Cookie、token 或主播身份码。
- 官方 live CMD 部分示例与正文不一致，价格含义/数量乘法、身份稳定范围和每种事件实际权限须用 fixture 定案。
